Use Kafka tools with Apache Iggy

Justin Mclean

Apache Iggy Contributor

The Kafka gateway lets Kafka clients and tools work with Apache Iggy. It speaks the Kafka protocol and stores the data in Iggy, so the only change on the client side is the bootstrap address.

This post shows how to start the gateway with an Iggy server, then connect kcat, the Kafka console tools, and Java and Python programs to it. You need Docker, git and kcat (brew install kcat on macOS, apt install kcat on Debian or Ubuntu), plus JDK 17 or later and Maven for the Java version, or Python 3.8 or later for the Python version.

What the gateway is

The gateway is a separate server that listens for Kafka clients on port 9093 by default. It translates each Kafka request into calls to the Iggy server and replies in Kafka's format, so to a client it looks like a Kafka broker.

It supports producing, fetching, listing offsets, topic and partition management, topic configs, and consumer groups with committed offsets stored in Iggy. A Kafka topic maps to an Iggy topic of the same name, inside one Iggy stream called kafka by default. A record's value becomes the Iggy message payload, and its key and headers become Iggy user headers. That means a Kafka consumer can read a topic that an Iggy SDK producer wrote, and the other way round, with an Iggy SDK from the 0.10.0 release or later (Rust SDK 0.12.0 or later).

The gateway ships as its own binary and Docker image, apache/iggy-kafka-gateway. It works with a stock Iggy server, 0.10.0 or later.

Start the gateway next to an Iggy server

The Iggy repository has a Compose file that starts two containers: iggy-server, an Iggy server from the apache/iggy:edge image, and iggy-gateway-kafka, the gateway built from source with its bridge to Iggy switched on. Clone the repository:

Then start both containers. The first start takes a few minutes while the gateway compiles:

Wait until docker compose ps shows both iggy-server and iggy-gateway-kafka as healthy. If Compose reports that a port is already in use, remove that port from the iggy-server service in docker-compose.yml, because this post only uses the gateway's port 9093.

The Kafka tool commands below run in the apache/kafka container, so you don't need to install Kafka, and use --network host so they reach the gateway at 127.0.0.1:9093, the same address kcat and the Java and Python programs use. On Docker Desktop, turn on host networking first, under Settings, Resources, Network (Docker Desktop 4.34 or later). If you have the Kafka tools installed on your machine, you can run them directly and drop the docker run prefix.

The records are ordinary Iggy messages. Use the Iggy CLI in the server container to read the first record the Java program wrote, with --show-headers to show where the Kafka key is stored. Run it from gateways/kafka:

Kafka and Iggy both number partitions from 0, so stream kafka, topic readings-java, partition 0, offset 0 is the record the Java consumer printed as partition=0 offset=0 key=sensor-0 value=reading 0. The value is the payload and the key is in the kafka.key user header, and the timestamp and ID will differ on your machine. If you ran only the Python version, poll readings-python 0 instead.

When you are done, docker compose down -v stops both containers and removes the data.

Current limits

The Compose file builds the gateway from the default branch, which has newer defaults than the 0.2.0 release. Until the next release, use the apache/iggy-kafka-gateway:edge image rather than latest, which is 0.2.0 and starts with the bridge off, so it stores nothing. The steps above cover producing, consuming and consumer groups, and a few Kafka features are not there yet:

  • Transactions are not supported. A transactional producer gets a clear error, and read_committed consumers work as normal.
  • An idempotent producer, like the default Java one, writes each batch once. Other producers, such as kcat, and all consumers get at-least-once delivery. To keep that through several Iggy nodes crashing at once, a topic needs persisted durability, as docs/IDEMPOTENCE.md describes.
  • Deleting records from a topic, for example with kafka-delete-records.sh, is not supported yet.
  • The gateway's end-to-end tests run kcat and the Kafka Java clients and tools, and the programs in this post also ran with kafka-clients 4.4.0 and 3.9.1 and kafka-python 3.0.13. A compatibility matrix for more clients and frameworks, such as Sarama, KafkaJS, Kafka Connect and Kafka Streams, is planned in apache/iggy#4531.

Where to go next

  • The gateway README has every setting, and the docs folder covers the record mapping, consumer groups, authentication and the supported API versions.
  • If you would rather change the constructors in your Java code than run a gateway, kafka-clients in apache/iggy-demos implements Kafka's Producer, Consumer and Admin interfaces on top of the Iggy SDK. You build the jar yourself and point bootstrap.servers at Iggy. Records use the gateway's format, but committed offsets do not yet, so a consumer group cannot move between the two.
  • Tell us which client or tool you tried and what happened, on GitHub or in the Iggy Discord.
